C++ library architecture

How an encrypted document moves through the C ABI, the stateful container, its services, and the revision format—and where the desktop host takes responsibility.

Native shared libraryVersioned C ABIRevised-v3 containerPortable history subset

01 · System boundary

The host handles files, journals, backups, UI, and publication. The library validates and authenticates bytes, manages one in-memory document session per context, and prepares exact encrypted candidates. The host must report the publication outcome before the library adopts a candidate.

ABI boundary

Opaque handles and sized byte spans keep internal C++ classes private. ABI functions translate internal failures to stable status codes.

Publication boundary

A candidate is an exact byte sequence held by Container. The host copies, journals, publishes, and verifies it.

Format boundary

The revised-v3 envelope protects the document key and payload. RevisionGraph validates decrypted history and content.

02 · Key classes and interactions

Arrows name the actual ownership or call relationship. Context owns services and the active container; the container borrows those services, owns the installed data, and asks the state manager to calculate transitions.

Stateful core Service boundary Format / authenticated data
src/core

Composition and policy

ServiceFactory builds the production registry. Each service has a virtual boundary for context-level substitution. PersistenceService delegates v3 envelope operations; HistoryService chooses compaction cutoffs.

src/container

Session and encryption

Container coordinates operations, while ContainerStateManagerService computes valid transitions and host effects. RevisedV3Container handles the encrypted envelope and wrapper table.

src/format

Authenticated history

RevisionGraph validates deterministic CBOR, immutable IDs, links, hashes, and reconstructable content. It can produce replacement graph bytes for saves, merges, events, and compaction.

src/document

Divergent replicas

MergeSave authenticates local and target containers, checks shared identity and rights, asks RevisionGraph to merge, then encrypts the result using target wrappers.

03 · Data flows for key user stories

Each strip follows the data from left to right. Ochre means the host or caller, green means the stateful core, blue means the ABI, and purple means encrypted-format or history code.

Open and read an existing document

The first stage checks public framing only. Clear content becomes available after password authentication and complete graph validation.

  1. HostRead target bytesPass an explicit byte span and length.
  2. C ABIcontainer_openCreates the active handle through Context.
  3. ContainerValidate framingPersistenceService checks the v3 envelope; state becomes locked.
  4. V3 + graphUnlock and validatePassword slot, payload AEAD, CBOR, IDs, links, and bodies.
  5. ContainerExpose permitted datacontainer_read returns an owned snapshot; history is copied into a separate graph handle.
An eligible editor may then attempt the advisory editing lease. Until its lease is confirmed, the session stays read-only. A temporary invitation must be claimed before clear reads.

Manual save and verified publication

Candidate preparation changes no committed image. The host owns the durable transaction and reports its exact outcome.

  1. HostSubmit working textConfirm edit lease and send canonical content with submit_content.
  2. Container + graphPrepare saveCheck rights/state; save_content creates a sealed revision.
  3. V3 envelopeEncrypt candidateFresh nonce; reauthenticate proposed bytes; retain operation ID and source head.
  4. HostJournal & publishCopy exact candidate, reread target, verify rights, then publish and verify.
  5. ContainerAcknowledge resultVerified success adopts bytes and data; definite failure discards; ambiguity retains candidate for reconciliation.
The same prepare → copy → host publication → acknowledgement pattern is used for slot, lease, activity, merge, and compaction candidates. resolve_save settles an ambiguous result after target reread.

Resolve divergent replicas

The user supplies resolved text; the library proves that the two authenticated containers represent related versions of the same document.

  1. HostObserve conflictCollect current target bytes, local replica, passwords, and resolved text.
  2. ContainerAssess or prepareassess_merge checks without retaining state; prepare_merge holds a candidate.
  3. MergeSaveAuthenticate bothCheck document ID, journal key, active slot, permissions, and graph lineage.
  4. RevisionGraphBuild resolved headKeep local content line; link the foreign head and preserve its metadata.
  5. Host + corePublish & acknowledgeEncrypt with target wrappers, publish exact bytes, then adopt only on verified success.
The API distinguishes unrelated targets, rollback, unavailable merge base, revoked access, and denied target permissions so the host can ask for the right decision.

Inspect an earlier revision

The history view receives its own graph handle, so it does not depend on borrowed pointers into the active container.

  1. HostRequest historyCall container_revision_graph after unlock.
  2. C ABICopy graphDecode the authenticated payload into an independently owned handle.
  3. RevisionGraphList and locatePage metadata; inspect heads and a selected revision ID.
  4. RevisionGraphReconstructReplay an available canonical body or report unavailable pruned/foreign content.
  5. HostDisplay & destroyUse owned result views and release page, result, and graph handles.

04 · State and ownership invariants

The state manager returns a new snapshot and required host effects; it does not authenticate bytes or perform I/O. Container verifies the relevant facts, installs transitions, then notifies observers.

ConcernOwnerInvariant
Active lifetimeContextOne active Container; close releases it before another lifecycle.
Access and editingContainerState + managerClosed/open, locked/unlocked, read-only/editing, lease, attention, and publication are separate axes.
Authenticated materialUnlockedContainerDataOwns document ID, slot identity, work-journal key, lease, and decoded graph. Its destructor clears fixed secrets and selected plaintext buffers, then releases the graph.
Pending publicationContainerCandidateAt most one unresolved candidate; a matching operation ID is required to acknowledge or resolve it.
Durable storageHostThe library returns encrypted bytes and effect hints; it does not write the target or local work journal.
History viewC ABI owned handlesGraph, page, result, snapshot, and slot views have explicit destroy functions and independent lifetimes.

Terminology: “lock” hides clear content on screen; the editing lease is advisory shared document state. A lease rewrite changes encrypted payload metadata without creating a revision. See the domain glossary.

05 · Build surfaces

Native

Full shared library

CMake builds src/abi, core, container, document, format, and security. It links libsodium. The optional Node-API addon in apps/windows/native adapts this C ABI for Electron.

Emscripten

Portable format subset

The WASM target compiles only revision/history ABI and format sources. It can validate and inspect already-decrypted format data, but has no password-container, lease, or publication path.
